# Bathymetry and Sediment-Model Tool Adoption Review

**Reviewed:** 2026-10-23  
**Status:** Evidence-based technology review; not a model approval, dependency declaration, or claim that any external engine has been integrated.  
**Scope:** Tri-State Systems Manager (TSM), with emphasis on inland Ohio–Wabash riverine flood and sediment decision support.

## Decision summary

**Do not add all listed projects as runtime dependencies.** They solve different problems, target different environments, and carry different validation and licensing conditions. Prefer thin, separately testable adapters and pinned external model executables over embedding full solvers in the browser or Python application's dependency environment.

Recommended order:

1. **Strengthen the existing HEC-RAS workflow contract first.** TSM already has HEC-RAS release-gate checks and a `ras2fim_tristate.py` entry point. Review the actual wrapper behavior and define the subprocess/input/output contracts before calling this a production solver integration. A valid gate or a script existing is not proof that a HEC-RAS project has been executed or scientifically validated.
2. **Use NASA ICESat-2 ATL13 as a potential independent, screening-level inland-water observation source**, only where product coverage and semantics fit. ATL13 is an inland-water product and includes a coarse depth-to-bottom-topography parameter; it is not a substitute for a calibrated hydrographic survey. ATL24 is the coastal/nearshore bathymetry product and should not be treated as the correct product for an inland river AOI.
3. **Retain MB-System as an optional survey-processing tool** when genuine multibeam/interferometric/sidescan sonar data are available. It is a bathymetry/backscatter processing package, not a general DEM acquisition service and not a hydraulic solver.
4. **Evaluate Delft3D and TELEMAC-GAIA/SISYPHE as specialist sediment/morphodynamics engines** in an isolated model-runner workstream after a real AOI, surveyed bed data, sediment inputs, boundary conditions, and validation reference are available. Pin releases and audit each module's license before deployment or redistribution.
5. **Keep Tinfour, ADCIRC_MATLAB, oceansdb, SWAN, OceanWave3D, and open_echo optional and purpose-specific.** Several are excellent tools for specialized subproblems but are not direct drop-in replacements for TSM's current TypeScript/Python stack or its principal inland river workflow.

### Important distinction: free-to-use, public domain, and open source are not interchangeable

Tool choice must be based on the exact upstream license and access conditions at the pinned version. HEC-RAS public-domain source status does not mean its runtime is installed in every environment. ADCIRC's official distribution conditions are restrictive relative to an unrestricted redistributable dependency. Delft3D and related ecosystems contain component-level license differences. Record the actual module, version, license, required attribution, redistribution terms and acquisition path in each adapter's manifest.

## Proposed integration contract

Every external solver adapter should implement a narrow, out-of-process contract rather than importing solver internals into the web console:

1. **Preflight:** report executable/version, platform, required modules, licensing acknowledgement, available input data, and missing capabilities. Do not auto-install or download multi-gigabyte solvers during a normal app startup.
2. **Input manifest:** bind AOI geometry/hash, source IDs and vintages, input checksums, CRS/axis order, horizontal units, vertical datum, coordinate epoch where applicable, grid/mesh resolution, bathymetry quality flags, sediment classes/properties, discharge and stage boundary conditions, time window, calibration/configuration and parameter values.
3. **Controlled execution:** use argument arrays (not shell-concatenated commands), strict path containment, finite timeout, bounded logs/output size, explicit cancellation, isolated work directories, and deterministic configuration. An unavailable engine returns a scoped unavailable/degraded result.
4. **Output contract:** solver/module/version, start/end time, return code, run log, output manifest and checksums, units/datum, spatial coverage, mesh/grid metadata, mass-balance/conservation diagnostics where available, warnings, and explicit missing/invalid output reasons.
5. **Scientific qualification:** separate calibration events from independent validation events. Compare water-surface elevation/stage, flow split, velocity where observed, inundation extent, and sediment/bed-elevation changes only when the relevant measurements exist. Report the performance metric, reference data, spatial/temporal support, uncertainty, and known failure modes.
6. **Evidence class:** external model results remain **SCENARIO** or **DERIVED** unless they meet a separately defined, exact authoritative/regulatory evidence requirement. A passing software test or solver exit code alone does not certify scientific correctness.

## Bathymetry and sediment-data quality gates

Before any morphodynamic run, require explicit evidence for:

- Survey source, acquisition time, navigation/positioning method, sonar/LiDAR method, processing software and version, calibration/QA records, and coverage.
- Horizontal CRS, axis order, units, geoid/reference surface if relevant, vertical datum, conversion grid/version, coordinate epoch where relevant, and water-level/tidal/stage correction method.
- Sounding spacing/resolution, measured versus interpolated cells, no-data mask, uncertainty/quality flags, minimum/maximum values, spikes/outliers, and source overlap disagreements.
- Sediment sampling date/location/depth, grain-size distribution and fractions, cohesive/non-cohesive classification where relevant, density/settling parameters when available, and provenance for any inferred parameter.
- For model boundaries: observed or authoritative discharge/stage time series, timestamps/timezone, units, station identity, datum semantics, boundary coverage, and the conditions used during calibration and independent validation.
- Reproducible run ID and manifest digest linking exact inputs, software versions, configuration, model outputs, metrics and reviewer notes.

Do not blend a terrestrial DEM and an underwater survey just because both are elevations. Resolve vertical datum and water-surface semantics explicitly, preserve data-source breaklines/uncertainty, and keep unsurveyed bed regions identified as gaps or modeled estimates. Do not transfer calibration from the Wabash/Ohio confluence study to a different reach or treat one modeled alternative as an approved design.

## Research leads (not production methods)

These papers are useful literature leads and should be evaluated against their full experimental conditions before any method is adopted:

- Angel et al., [*Bathymetry reconstruction from experimental data using PDE-constrained optimisation*](https://arxiv.org/abs/2404.05556) (2024 preprint). The study reports qualitative reconstruction of a Gaussian-shaped wave-flume bathymetry using sparse sensor measurements; it does not establish a generally reliable substitute for field bathymetric survey.
- Travert et al., [*Evaluation of Performance Measures for Qualifying Flood Models with Satellite Observations*](https://arxiv.org/abs/2408.00571) (2024 preprint). The study shows that performance-metric choice can affect model qualification/calibration with a single flood image. TSM should use more than one metric and document observation error and coverage.
- Garin et al., [*Comparative Analysis of TELEMAC-2D Models on Agricultural Flood Damage Estimates*](https://arxiv.org/abs/2504.17344) (2025 conference paper/preprint). The comparison reports that model parameters and topo-bathymetry projection can materially affect damage estimates, especially where a few high-vulnerability fields dominate the total. This supports sensitivity testing, not wholesale transfer of the study's parameters.

- [ ] Audit the current HEC-RAS/ras2fim code path, identify which commands genuinely execute solvers versus print workflow guidance, and add an execution contract test only for supported real inputs.

- [ ] Add a second solver only when input/output compatibility, runtime constraints, component licenses and benchmark acceptance criteria are documented.
