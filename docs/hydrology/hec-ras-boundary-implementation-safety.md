# HEC-RAS boundary and geometry implementation safety

**Status: design/validation only; HEC-RAS execution remains blocked.**

The proposed scripts shared in the project conversation are not safe to use as
operational writers without verification against files generated by the installed
HEC-RAS version and its official documentation.

## Required corrections

- Do not create arbitrary groups or datasets inside `.g01` files. HDF5 being
  readable/writable does not mean a dataset is part of the HEC-RAS geometry
  contract. Use a version-specific, validated geometry-generation workflow and
  preserve a byte-for-byte backup before any approved mutation.
- Do not emit a `.u01` file from guessed key names or padded numeric records.
  Start from a minimal file generated by the target HEC-RAS release, then test
  a deterministic, narrowly scoped transformation against that version's
  documented file grammar. A text file that looks plausible is not proof that
  HEC-RAS will parse or apply it.
- Do not launch `Ras2D.exe` with guessed flags. The orchestrator must remain
  dry-run-only until the installed engine's supported automation interface,
  licensing, exit semantics, timeout behavior, and output validation are tested.
- Do not estimate Froude number from discharge alone. It requires hydraulic
  state and geometry (at minimum velocity and hydraulic depth, or equivalent
  section/mesh calculations). The validator therefore requires a supplied
  geometry-derived `froude_number` per non-missing flow record and treats it
  only as screening evidence.
- A configured USGS station ID is not proof of live telemetry or boundary
  representativeness. An authorized source adapter must obtain and retain
  timestamped source responses, qualifiers, units, gauge metadata, and hashes.
  The validator's `telemetry_evidence` is a contract input, not a live-USGS
  client or independent attestation verifier.
- The proposed station-to-boundary mapping, 15-minute interval, slope range,
  and Froude threshold are project screening policy inputs, not regulatory
  determinations or a substitute for qualified hydraulic review.

## Boundary CSV contract

The validator in `tsm_runtime/boundary_flow_validator.py` accepts columns:

`timestamp,flow_cfs,froude_number`

Timestamps must include a UTC offset or `Z`. Missing timestamps on the expected
interval grid count as missing records. Blank flow or Froude cells are missing
values. The current default interval is 15 minutes; maximum consecutive missing
records is 2; maximum missing fraction is 1%; the supplied maximum Froude must
be strictly less than 0.85. Normal-depth slope is screened to 0.0001–0.0008 ft/ft.
All thresholds are configurable project policy and require engineering approval.

A successful result is `VALIDATED_FOR_REVIEW`, never execution authorization.
Every result explicitly reports `execution_allowed: false`. HEC-RAS execution
requires separate authorization, a verified geometry and boundary mapping, source
provenance, and a version-tested input writer.

## Release gates still required

1. Verify gauge identities, station metadata, current data freshness, qualifiers,
   units, and actual telemetry through the authorized USGS source adapter.
2. Verify the physical representativeness of each gauge and the upstream/downstream
   boundary placement with a qualified hydrologist/hydraulic engineer.
3. Verify terrain resolution, vertical datum, bathymetry, cross-border coverage,
   breaklines, mesh spacing, and boundary geometry from actual project artifacts.
4. Test against a known-good `.g01` / `.u01` generated by the deployed HEC-RAS
   version and confirm solver acceptance in an isolated test project.
5. Add numerical convergence checks that inspect solver-generated diagnostics and
   water-surface outputs; process exit code alone is not proof of convergence.
6. Keep the production AOI unapproved until its jurisdiction overlays, outlet,
   terrain, boundary inputs, and human approval are verified.
